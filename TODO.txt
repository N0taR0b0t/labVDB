What needs the most attention next

1. Bring documentation in sync with the code
- Current risk:
  - repository docs still describe several already-completed limitations
- Why it matters:
  - future implementation decisions will be based on false assumptions
  - review and planning become harder than necessary
- Required changes:
  - keep `TODO.txt` focused on remaining work only
  - update `CONTEXT.md` to distinguish current behavior from planned server-mode features
  - add a concise README with:
    - setup
    - indexing commands
    - API usage
    - known limitations

2. Make hybrid retrieval real, not just planned
- Current state:
  - lexical scoring and hybrid reranking helpers exist
  - `/search` still performs dense retrieval only
- Why it matters:
  - scientific terms, abbreviations, assay names, genes, and units often need lexical support
- Required changes:
  - rerank dense candidates with the existing lexical signal
  - optionally expose a query parameter to compare dense-only vs hybrid behavior
  - evaluate result quality on a small set of real lab queries

3. Add stronger search filters and result controls
- Current state:
  - search supports `doc_id` and `filename`
- Why it matters:
  - larger corpora will need tighter narrowing and more controllable output
- Required changes:
  - add `section` filtering
  - add pagination or cursor-style result navigation
  - return richer result metadata where useful:
    - section
    - total pages
    - source path or a safer alias
  - consider snippet windows that emphasize the matched part of a chunk

4. Improve operational visibility
- Current state:
  - indexing prints basic timing totals
  - search has a minimal `/stats` endpoint
  - a local benchmark harness now exists for sample-based indexing and query throughput checks
- Why it matters:
  - without measurements, optimization work is guesswork
- Required changes:
  - log query latency, embedding latency, and Qdrant latency
  - expose manifest status counts in `/stats` or a new admin endpoint
  - extend the benchmark coverage to report:
    - chunk count per document
    - cold-start versus warm-start comparisons
    - larger sample or full-corpus runs

5. Clean up text extraction and chunk quality
- Current state:
  - block cleanup and section normalization exist
  - extraction is still vulnerable to PDF noise
- Why it matters:
  - low-value chunks increase index size and reduce precision
- Required changes:
  - better header/footer suppression
  - more robust handling of references-heavy pages
  - improved paragraph grouping for multi-column PDFs
  - optional heuristics to down-rank or drop low-information chunks

6. Add focused validation coverage
- Current gap:
  - there is no lightweight automated check for ingest correctness or retrieval regressions
- Why it matters:
  - index behavior can silently drift as chunking and ingest logic evolve
- Required changes:
  - expand tests for:
    - `doc_id` stability
    - duplicate detection
    - filter construction
    - section-aware chunk boundaries on real extracted pages
    - rename / remove / reindex behavior
  - add a tiny regression query set for manual or scripted relevance checks

Architecture pivot — scaling to ~20,000 PDFs

The following phases implement the core design change: Qdrant for vector search only,
SQLite manifest as authority, SQLite chunk store for full text.

Critical phases (prerequisite for scaling):

Phase 1 — Deploy server Qdrant [COMPLETE]
- DONE: QdrantClient(url=QDRANT_URL) when env var set, embedded fallback otherwise
- DONE: scalar quantization + on_disk_payload on collection creation
- DONE: UnexpectedResponse 400 silenced in ensure_payload_indexes(); 5xx propagates
- DONE: lifespan-managed client; no import-time Qdrant calls
- DONE: /health endpoint; docker-compose.yml; .env.example

Phase 2 — Make manifest authoritative, remove collection scans [COMPLETE]
- DONE: plan_index_jobs() uses manifest for skip/change detection; no fetch_doc_ids() call
- DONE: changed-file delete fires unconditionally (Qdrant no-op if absent)
- DONE: count_indexed_docs() replaces count_unique_doc_ids() in /stats
- DONE: --reconcile CLI command (single scroll, read-only, maintenance only)
- DONE: pymupdf import deferred; planner is importable without PDF library

Phase 3 — Move full chunk text out of Qdrant payloads [COMPLETE]
- DONE: chunks.sqlite3 with (chunk_id, doc_id, full_text); index on doc_id
- DONE: flush_records writes SQLite before Qdrant upsert; payload has preview (200 chars) not text
- DONE: delete_document cleans Qdrant then chunk store
- DONE: /search returns preview + chunk_id; no full text in response
- DONE: GET /chunk/{chunk_id} fetches full text from SQLite on demand; 404 if missing

Supplemental phase (improves perceived speed; not required for scaling):

Phase 4 — Progressive result loading and UI filters
- Return only filename, page, section, snippet, and score in initial search response
- Load full chunk text on demand when the user opens a result
- Add UI filters for filename, document, and section

Migration note: switching to server Qdrant requires a full re-index. Run indexer.py --force
after deploying Phase 1. The manifest tracks all state needed for the re-index pass.
